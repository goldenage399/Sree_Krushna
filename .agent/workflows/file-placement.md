# Unified File Placement Workflow

> **MANDATORY**: Run this workflow BEFORE creating ANY new file (code or documentation).
> **Replaces**: `/file-placement-guardrail` (now merged here)

---

## Step 0: CONSULT DOCUMENTATION HUBS FIRST (Mandatory)

> [!IMPORTANT]
> **Before ANY placement decision**, you MUST consult these sources to understand existing organization:

### 0.1 Primary Reference Documents

| Hub | Location | What It Tells You |
|-----|----------|-------------------|
| **Project-Wide Hub** | `docs/DOCUMENTATION_HUB.md` | All docs by semantic domain, file naming conventions, what exists where |
| **Module SSOT Hubs** | `docs/{Module}_Module_SSOT/00_DOCUMENT_HUB.md` | Module-specific organization, document inventory, ID sequence |
| **Core Function Index** | `docs/CORE_FUNCTION_INDEX.md` | Existing utility functions, patterns, helpers |

### 0.2 Mandatory Checks

// turbo-all
1. **Search DOCUMENTATION_HUB.md** for your content's semantic domain
   - Check if topic already has a designated SSOT location
   - Note existing naming patterns for similar files
2. **Check relevant Module SSOT Hub** for document inventory
   - Look at existing DOC_IDs to get next ID
   - See existing file organization structure
3. **Search for similar existing files** using `grep_search`:
   ```
   grep_search Query="your_topic" docs/
   ```

### 0.3 What Doc Hubs Reveal

The Documentation Hubs contain:
- **Semantic Domain Mapping**: Which topics go where
- **Document Inventory**: What already exists (avoid duplicates)
- **Cross-Reference Matrix**: How docs relate to each other
- **File Location Reference**: Which code files → which docs
- **Change Log**: History of doc updates

**Example**: Before creating `ARCHITECTURE_Cache.md`:
1. Open `docs/DOCUMENTATION_HUB.md`
2. Search for "cache" or "performance" domains
3. Check if `Accounts_Module_SSOT` already has caching docs
4. See naming pattern: `ARCHITECTURE_*.md` for system design
5. Get next DOC_ID from `00_DOCUMENT_HUB.md`

## Step 1: Code Placement (Frontend/Backend)

### 1.1 Frontend Code → `public/js/`
```
public/js/
├── modules/{module}/     # Feature modules (expense/, accounts/, ledger/)
│   ├── {Module}Module.js       # Entry point
│   ├── {Module}Service.js      # API calls
│   ├── renderers/              # UI renderers
│   └── tests/                  # Frontend tests
├── components/           # Reusable UI components
├── services/             # BackendService, ValidationService
├── state/                # StateManager
└── utils/                # Pure utility functions
```

### 1.2 Backend Code → `backend/src/`
```
backend/src/
├── 00_*.js              # Shared utilities (Config, PatternG, WriteJournal)
├── 01_Auth.js           # Authentication
├── 02_Router.js         # Request routing
├── modules/             # Feature modules
│   └── {module}/
│       ├── XX_*_Router.js     # API handlers (deployed)
│       ├── XX_*_Service.js    # Business logic
│       └── XX_*_Writer.js     # Sheet writers
└── 99_TestScripts_*.js  # Backend tests (consolidated, not disposable!)
```

**⚠️ NEVER edit `backend/gas_prod_snapshot/`** - Auto-generated by deploy script.

## Step 2: Documentation Placement (Intelligent Classification)

### 2.1 Decision Tree for Documentation

```
Creating documentation?
│
├─ Q1: Does it describe a CROSS-CUTTING pattern (affects 2+ modules)?
│   └─ YES → Step 2.2 (Cross-cutting placement)
│
├─ Q2: Is it MODULE-SPECIFIC architecture/schema/flow?
│   └─ YES → Step 2.3 (Module SSOT placement)
│
├─ Q3: Is it ENHANCEMENT-SPECIFIC (tied to a PIO-XXX)?
│   └─ YES → Step 3 (Enhancement notes)
│
├─ Q4: Is it PROJECT-WIDE reference (DOCUMENTATION_HUB, CORE_FUNCTION_INDEX)?
│   └─ YES → `docs/` (root level)
│
└─ Q5: Temporary/user-created?
    └─ YES → `User_Created/`
```

### 2.2 Cross-Cutting Patterns

**Location**: `docs/{PrimaryModule}_Module_SSOT/` (where most impact is)

**Examples**:
- `ARCHITECTURE_3_LAYER_CACHE.md` → `docs/Accounts_Module_SSOT/` (affects Accounts most)
- `ARCHITECTURE_WriteJournal.md` → `docs/` (root, affects all modules equally)

**Must Also**:
1. ☐ Add to primary module's `00_DOCUMENT_HUB.md`
2. ☐ Add cross-references in affected modules
3. ☐ Update `docs/DOCUMENTATION_HUB.md` if project-wide

### 2.3 Module SSOT Placement

```
docs/{Module}_Module_SSOT/
├── 00_DOCUMENT_HUB.md          # Navigation hub (required)
├── ARCHITECTURE_*.md           # System design
├── MODULE_*.md                 # Module overview
├── DATA_FLOW_MAP.md            # UI → JSON → Sheet mapping
├── CONTRACT.json               # API contracts
├── SHEET_SCHEMAS.md            # Sheet column definitions
├── SSOT_*.md                   # Authoritative references
├── VALIDATION_Rules.md         # Field validation
└── README_*.md                 # Feature-specific guides
```

**Naming Conventions**:
| Pattern | Purpose | Example |
|---------|---------|---------|
| `ARCHITECTURE_*.md` | System design | `ARCHITECTURE_MultiStepWizard.md` |
| `MODULE_*.md` | Module overview | `MODULE_ACCOUNTS.md` |
| `SSOT_*.md` | Authoritative reference | `SSOT_FUNCTIONAL_MAP.md` |
| `README_*.md` | Feature guides | `README_PIO085_TailScan.md` |

## Step 3: Enhancement Notes Placement

### 3.1 Classification (Protocol 6)

```
Enhancement complexity?
│
├─ ≤ 2 days (simple) → Entry in ENHANCEMENTS.md ONLY (no folder)
│
└─ > 2 days (complex) → enhancement-notes/
    ├─ 3-7 days (medium) → enhancement-notes/ENHANCEMENT_PIO-XXX_Title.md
    └─ 2+ weeks (large) → enhancement-notes/PIO-XXX-Module-Name/
                              ├── 00_ENHANCEMENT_INDEX.md
                              ├── ARCHITECTURE_*.md (if exists, MOVE to SSOT after close!)
                              └── ...
```

### 3.2 Post-Enhancement Migration

> [!IMPORTANT]  
> **When enhancement closes**: Architecture docs that are PERMANENT should be MOVED to `docs/{Module}_Module_SSOT/`

**Keep in enhancement-notes**:
- Enhancement-specific planning (PHASE_PLAN.md)
- Implementation decisions (DECISION_*.md)
- External reviews (Critical_Analysis_Report.md)

**Move to SSOT**:
- Architecture patterns (ARCHITECTURE_*.md)
- Module schemas (SHEET_SCHEMAS updates)
- Permanent how-to guides (README_*.md)

## Step 6: Registration Requirements

After placing file, MUST register in appropriate hubs:

### 6.1 For New Documentation

| Location | Register In |
|----------|-------------|
| `docs/` (root) | `docs/DOCUMENTATION_HUB.md` |
| `docs/{Module}_Module_SSOT/` | That module's `00_DOCUMENT_HUB.md` |
| `enhancement-notes/` | `enhancement-config.json` (via skill) |

### 6.2 For New Code

| Location | Register In |
|----------|-------------|
| New utility function | `docs/CORE_FUNCTION_INDEX.md` |
| New API action | `docs/{Module}_Module_SSOT/CONTRACT.json` |
| New sheet column | `docs/{Module}_Module_SSOT/SHEET_SCHEMAS.md` |

## Step 7: ENFORCEMENT MECHANISM (How Doc Hubs Stay Updated)

> [!CAUTION]
> **Creating a new doc WITHOUT updating the relevant Hub = PIRR FAILURE**

### 7.1 Automated Detection (PIRR Category #5)

The PIRR checklist (`pirr-compliance` skill) includes:

```
Category #5: Documentation Hub Sync
☐ If new docs created in docs/{Module}_Module_SSOT/ → Updated 00_DOCUMENT_HUB.md?
☐ If new docs created in docs/ root → Updated DOCUMENTATION_HUB.md?
☐ If new architecture docs → Added to cross-reference matrix?
```

### 7.2 Verification Commands

// turbo-all
Before closing any session, run these checks:

```powershell
# Check for orphan docs (exist but not in hub)
git diff --name-only HEAD~5 | Select-String "docs/.*\.md$"
# Compare output with DOCUMENTATION_HUB.md entries
```

### 7.3 Hub Update Checklist

When adding ANY new file to `docs/{Module}_Module_SSOT/`:

1. ☐ **Get next DOC_ID** from `00_DOCUMENT_HUB.md` inventory table
2. ☐ **Add entry** to appropriate tier (Tier 1-4)
3. ☐ **Add cross-reference** row if affects multiple topics
4. ☐ **Update change log** at bottom of hub
5. ☐ **Update Last Updated** date in frontmatter

### 7.4 Failure Consequence

If PIRR detects orphan docs:
```
PIRR Category #5 FAIL: New file detected without hub registration
→ Orphan: docs/Accounts_Module_SSOT/ARCHITECTURE_3_LAYER_CACHE.md
→ Missing from: 00_DOCUMENT_HUB.md
→ ACTION REQUIRED: Add to document inventory before merge
```

## Anti-Patterns to Avoid

| ❌ Anti-Pattern | ✅ Correct Approach |
|-----------------|---------------------|
| Creating ARCHITECTURE docs in enhancement-notes permanently | Move to SSOT when enhancement closes |
| Standalone `99_temp.js` test files | Append to `99_TestScripts_{Module}.js` |
| Docs in project root | Use `docs/` folder |
| New naming patterns | Follow existing conventions |
| Skipping hub registration | Always update relevant hubs |
| Hardcoded magic values | Add to `00_Constants.js` or config |

## Quick Reference: Impact Analysis

Before placing, consider:

| Factor | Question | If YES → |
|--------|----------|----------|
| **Scope** | Affects multiple modules? | Cross-cutting placement |
| **Lifetime** | Will outlive the PIO? | Module SSOT, not enhancement-notes |
| **Discovery** | Should be easily found? | Add to Document Hub |
| **Dependencies** | Other code depends on it? | Document in CORE_FUNCTION_INDEX |
| **Contract** | Defines API/schema? | Update CONTRACT.json/SHEET_SCHEMAS |

## Workflow Execution Summary

// turbo-all
1. **Step 0**: CONSULT DOCUMENTATION HUBS (mandatory!)
   - Read `docs/DOCUMENTATION_HUB.md` for semantic domain mapping
   - Check relevant module's `00_DOCUMENT_HUB.md` for existing inventory
   - Search for similar existing files
2. **Classify** file type (code/doc/enhancement/config/test)
3. **Apply** placement rules from relevant section above
4. **Create** file in correct location
5. **Register** in appropriate hubs (Step 6)
6. **Cross-reference** if content affects multiple modules

**If unsure**: ASK the user before creating!
