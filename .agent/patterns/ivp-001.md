# IVP-001 — Investigation Validation Protocol

This protocol is a repository-wide standard mandatory for every debugging, troubleshooting, and investigation task. It ensures that hypotheses are systematically tested, evidence is strictly cataloged, and no remediation is proposed without empirical validation.

---

## 1. Investigation Phases

| Phase | Required Inputs | Expected Outputs | Exit Criteria |
| :--- | :--- | :--- | :--- |
| **Phase 1: Observation** | Error logs, bug report, or symptom description. | A clear, unambiguous definition of the observed malfunction. | Symptom is captured in writing with stack traces/context. |
| **Phase 2: Evidence Collection** | Current codebase state, active database documents, user claims. | Raw factual data from the environment. | All relevant configuration and data states are collected. |
| **Phase 3: Hypothesis Generation** | Collected evidence and codebase structure. | A list of at least two competing hypotheses. | Hypotheses list is written down; no single-cause bias. |
| **Phase 4: Hypothesis Ranking** | Competing hypotheses. | Ranked hypotheses based on likelihood. | Hypotheses are ordered from most to least likely. |
| **Phase 5: Falsification** | Hypotheses and falsification tests. | Falsified hypotheses with contradicting evidence. | Each hypothesis is subjected to a test designed to disprove it. |
| **Phase 6: Root Cause Confirmation** | Surviving hypothesis. | Direct empirical proof of the failure mechanism. | The failure mode has been isolated and demonstrated. |
| **Phase 7: Remediation Design** | Confirmed root cause. | Proposed code/config modification. | Fix is mapped directly to the root cause evidence. |
| **Phase 8: Validation** | Implemented fix. | Passing tests, updated logs, or emulator proof. | Direct proof that the failure no longer occurs. |

---

## 2. Evidence Hierarchy

All claims made during an investigation must be classified and ranked by the following levels of confidence. Level 5 evidence alone may **never** justify a code or configuration change.

* **Level 1: Direct Runtime Evidence** (Highest Confidence)
  - Logs, debugger state, emulator executions, or direct database states.
* **Level 2: Source Code**
  - AST scans, static file rules, or local compilation outputs.
* **Level 3: Documentation**
  - Official framework specifications or internal SSOT/hubs.
* **Level 4: Historical Incidents**
  - Past issues, resolved tickets, or discussion threads.
* **Level 5: Intuition / Memory** (Lowest Confidence)
  - Unverified assumptions, "best guesses," or memory of how a system works.

---

## 3. Hypothesis Ledger

Every active investigation must maintain a live hypothesis table. No hypothesis may be silently abandoned.

| Hypothesis | Supporting Evidence | Contradicting Evidence | Status |
| :--- | :--- | :--- | :--- |
| _[H-ID]: Short description_ | _Level of evidence + source_ | _Level of evidence + source_ | `Active` \| `Rejected` \| `Confirmed` |

---

## 4. Evidence Ledger

Every factual claim must identify its exact source to prevent inferred assertions from being presented as direct observations.

* **Claim**: The assertion being made (e.g., "The projectId in the database is ffc_delta").
* **Source**: The exact tool, log, or query used (e.g., `firestore_get_document tasks/sML4nB7bS4VQo9SIZeRG`).
* **Confidence**: `Verified` (direct L1/L2 check) or `Inferred` (derived from other facts).

---

## 5. Confidence Rules

Confidence assertions must be strictly evidence-derived:

* **High Confidence** is permitted **only** when there are **two independent Level 1 evidence sources** OR **direct runtime reproduction** of the failure mode.
* **100% Confidence** is reserved **exclusively** for directly demonstrated root causes.
* **Otherwise**, confidence must remain **Moderate** or **Low**.

---

## 6. Remediation Gate

A remediation proposal (code edit or config change) **cannot** be generated until all of the following conditions are met:

* [ ] The failure mode has been directly demonstrated.
* [ ] All competing hypotheses have been explicitly evaluated.
* [ ] The evidence ledger is complete.
* [ ] The root cause has been isolated and confirmed.
* [ ] The remediation maps directly and exclusively to the confirmed evidence.

---

## 7. Self-Audit

Before submitting any final response or code change, perform this self-audit:

1. _Which statements in my analysis are directly verified?_
2. _Which statements are inferred?_
3. _What assumptions remain untested?_
4. _Could a cheaper verification (e.g., doc lookup or index check) invalidate my conclusion?_

If a cheaper verification is possible, it **must** be executed before responding.
